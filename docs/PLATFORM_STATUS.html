DOSBox-X Multiplatform — Platform Status

One Flutter front end over the DOSBox-X core, on Android, iOS and Linux. This page records, per platform, how the native core is bundled, what code is platform-specific, and where the three builds diverge.

Last updated: 2026-08-19. The native core is built and ABI-verified on all three platforms; a shipped, core-backed APK/IPA/App has not been cut yet, and audio is not yet runtime-verified on a device. See PLATFORM_STATUS.md for the detail.

Shared across all three platforms

Everything below is compiled/interpreted identically on Android, iOS and Linux.

  • flutter_app/lib/ — the whole app: 37 Dart files across screens/, services/, widgets/, theme/, data/, ffi/. All UI and all GUI/layout code lives here; there is no per-platform layout.
  • native/dosbox_core/bridge/dosbox_bridge.{h,cpp} — the C ABI. One contract, implemented once, linked against DOSBox-X on every platform.
  • pubspec.yaml — one dependency set: ffi, path, file_picker, shared_preferences, path_provider, gamepads, archive.

Per-platform

Android

  • Core bundling — libdosboxcore.so ships in flutter_app/android/app/src/main/jniLibs/<abi>/ and is loaded by bare name. Built by native/dosbox_core/android/build.sh (9 patches, cross-built per ABI: arm64-v8a, x86_64).
  • Platform-specific code — MainActivity.kt (gamepad hookup + manual SDL JNI init + storage permissions), AppRestartActivity.kt (process restart), org/libsdl/app/*.java (11 files, SDL2 Java glue), native/dosbox_core/android/patches/ (9 DOSBox-X source patches).
  • Divergence — the heaviest platform. SDL2's Android backend assumes its host is SDLActivity; ours is a FlutterActivity, so SDL JNI is initialised by hand.

iOS

  • Core bundling — libdosboxcore.framework inside Runner.app/Frameworks/, dlopen'd by path. Built by native/dosbox_core/ios/build-ios.sh (Docker cross-build).
  • Platform-specific code — AppDelegate.swift, SceneDelegate.swift (standard Flutter iOS), Runner-Bridging-Header.h, and the apply-ios-*.py scripts.
  • Divergence — framework (not loose dylib) because iOS code-signs every nested Mach-O in Frameworks/; no SDL Java glue or JNI anywhere.

Linux

  • Core bundling — libdosboxcore.so next to the executable; dev path derived from the repo root. Built by native/dosbox_core/linux/build.sh.
  • Platform-specific code — my_application.cc (standard Flutter/GTK); nothing else.
  • Divergence — the reference/dev platform. Gamepads work through the desktop plugin path (no activity subclass needed).

Review notes

1. Docs were stale, now fixed. README.md and docs/NATIVE_BUILD.md previously said the bridge was "not implemented"; it is implemented (dosbox_bridge.cpp, ~1000 lines) but not yet compiled against a real DOSBox-X tree. Both are corrected, and the audio/shutdown gaps are called out.
2. Android is by far the most customised platform — the SDL Java glue plus the manual SDL-JNI bootstrap plus 9 patches is real, load-bearing complexity that iOS and Linux simply do not have. Worth a second look once the core is running: the org.libsdl.app.* stubs and the hand-rolled SDL.setupJNI() path are the highest-risk parts and should not grow.
3. GUI/layouts are fully shared — confirmed nothing in android/res, ios/*.storyboard, or linux/ carries layout; all screens and widgets are in lib/.
4. Cores built on all three platforms, no shipped app yet — Linux (linux/build/libdosboxcore.so, boot-tested), Android (arm64-v8a + x86_64 in jniLibs/), iOS (ios/build/out/libdosboxcore, arm64 Mach-O). A core-backed APK/IPA/App has not been produced, and no device has booted one.
5. The shared ~/dosbox-x-pic tree is single-config — Android reconfigures it in place for the NDK; build-core-pic.sh now detects a cross config or foreign-arch objects and reconfigures + cleans before a host build. Run it before linux/build.sh whenever the tree was last used by Android. iOS clones its own tree in the container and is unaffected.
